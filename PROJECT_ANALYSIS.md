# Анализ проекта CL30

## 1) Что это за проект
- Монорепозиторий из двух частей:
  - `backend` на FastAPI + MongoDB (motor), с REST + WebSocket для чата.
  - `frontend` на React (CRA + CRACO + Tailwind + Radix UI), где есть два режима: локальный "песочница/демо" (`ChatApp`) и реальный чат с API (`RealChat`).

## 2) Архитектура и текущая зрелость
- **Бэкенд** реализует базовый жизненный цикл: регистрация, логин/логаут, список пользователей, отправка/получение сообщений, список диалогов, ws-канал для `typing`/новых сообщений.
- **Фронтенд** богат по UI и сценариям (много модалок, подарков, админ-команд и пр.), но часть функциональности работает через `localStorage` и mock-данные.
- В проекте есть задел на эксплуатационность фронтенд-сборки (health-check плагин и endpoint-ы для dev-сервера), что нетипично для простого CRA-шаблона и выглядит как хорошая инженерная практика.

## 3) Сильные стороны
1. Быстрый старт MVP-чата: есть и HTTP API, и WebSocket-поток.
2. Понятный раздел API в `frontend/src/services/api.js` и отдельный класс для WS.
3. Продуманная dev-инфраструктура фронтенда: флаги `ENABLE_HEALTH_CHECK`, `REACT_APP_ENABLE_VISUAL_EDITS`, управление watch/hot reload.
4. Уже есть артефакты предыдущего тестирования (`test_reports/iteration_*.json`) с высокой успешностью по фронтенд-сценариям.

## 4) Основные риски и технический долг (по приоритету)

### Высокий приоритет
1. **Небезопасная аутентификация на бэкенде**
   - Пароли хэшируются через обычный `sha256` без соли/адаптивности.
   - Токен самодельный (`sha256 + _userId`), без подписи/JWT, ротации, TTL и claims.
   - Это критичный риск при выходе в production.

2. **Логическая несогласованность состояния online/offline**
   - В `register` в БД сохраняется `isOnline=False`, но в ответе возвращается `isOnline=True`.
   - Это может приводить к рассинхрону UI в момент первичной регистрации.

3. **Сильная зависимость части UX от localStorage/mock-слоя**
   - Большой кусок функциональности (`ChatApp`) живет как оффлайн-демо, а не как единая доменная модель с backend.
   - Риск: расхождение бизнес-логики между демо-режимом и real-режимом (`RealChat`).

### Средний приоритет
4. **Отсутствие явного разделения слоев на бэкенде**
   - В одном `server.py` смешаны модели, auth, API-роуты, websocket-логика, startup/shutdown.
   - Поддерживаемость и тестируемость будут ухудшаться с ростом фич.

5. **CORS разрешён для всех origins**
   - Для dev нормально, для production рискованно без whitelisting.

6. **Нет явных автоматизированных unit/integration тестов в кодовой базе**
   - Есть отчеты о ручном/агентском тестировании, но мало программной регрессии.

## 5) Рекомендуемый план улучшений

### Этап 1 (безопасность и корректность)
- Заменить хэш паролей на `bcrypt`/`argon2`.
- Перейти на JWT (или opaque token + сессионное хранилище с TTL).
- Добавить срок жизни токена и принудительный logout/revoke по сессии.
- Устранить рассинхрон `isOnline` в `register`.

### Этап 2 (архитектура)
- Разделить backend на модули: `routers/`, `services/`, `repositories/`, `schemas/`, `core/security`.
- Вынести websocket manager и auth-dependency в отдельные файлы.
- Стабилизировать доменную модель, чтобы `ChatApp` и `RealChat` не расходились по правилам.

### Этап 3 (качество)
- Добавить минимум тестов:
  - backend: auth happy-path + negative cases, send/get messages, conversations pipeline;
  - frontend: smoke e2e на login/search/send message.
- Добавить CI (lint + tests + build).

## 6) Краткий вывод
Проект уже выглядит как **рабочий MVP мессенджера** с сильным UI и базовым realtime-контуром. Главный блокер для production — **безопасность auth/token** и **консистентность архитектуры между mock/local и real API**. После устранения этих пунктов можно относительно быстро выйти на более надежный beta-уровень.
